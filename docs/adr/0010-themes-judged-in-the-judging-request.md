# Themes are judged by the Agent, in the judging request it already makes

Whether a Hackathon is about a person's Themes needs judgement, so the Agent decides it as part of judging rather than the engine matching keywords: when the Profile has Themes, the judging prompt gains one question and the schema two required fields, `theme_fit` (`on_theme`, `open_themed` or `off_theme`) and `theme` (the matched Theme, copied from the Profile's list, or `null`). It is not a separate request, so it costs no extra Agent steps, and with no Themes the prompt and schema are exactly as before. The CLI still validates the answer against the schema (ADR 0004) and rejects a judgement whose Theme fields are missing when asked. What the fields say is normalised rather than rejected, because rejecting sends the whole batch of Candidates back to the queue, and an Agent that answers sloppily every time would stall judging Run after Run. An on-Theme answer naming no Theme, or one that isn't the person's (such as "AI" for "AI agents"), counts as open-themed. An open-themed or off-Theme answer that names a Theme keeps its verdict and drops the Theme. Theme fields given when none were asked are ignored. Each Run prints how many answers it normalised.

An open-themed Hackathon (participants may build anything) Fits any Themes, since the person could build on their own subject there; only one clearly about something else is off-Theme. We chose this over Fitting only on-Theme Hackathons because most hackathons are open-themed, and dropping them would hide most of what a person can attend.

Each answer is stored with the Themes it was asked about. An answer only holds for those Themes: a judgement made before the person set Themes, or about Themes they've since changed, Fits until a recheck asks about the current ones. Nothing is re-judged all at once when Themes change; rechecks reach these Hackathons on their usual schedule, and off-Theme ones (for the current Themes) aren't rechecked.
